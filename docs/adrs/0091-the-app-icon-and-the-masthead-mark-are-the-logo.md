# ADR 0091 — The app icon, the favicon and the masthead mark are the same logo, drawn from one SVG

**Date:** 2026-08-15
**Status:** Accepted
**Supersedes:** nothing. Amends [ADR 0008](0008-desktop-app-supervises-services.md)'s 2026-07-17
update (the app icon is no longer a generated amber bulb) and closes the mark-only-asset request the
design handoff left open under
[ADR 0052](0052-curator-is-three-places-not-a-nine-state-queue.md).

## Context

Marquee had two brand images and neither of them was the logo.

**The masthead mark** was a 52×52 crop of `marquee-logo.jpeg` — the hand-inked disc, sound waves,
tonearm and grid over the word MARQUEE, photographed on off-white paper. The crop was an
`overflow:hidden` box holding the image at `width:130px`, offset `left:-38px; top:-8px`, with
`mix-blend-mode:multiply` to merge the photographed paper into `--pp-paper`. The design handoff that
introduced it ([ADR 0052](0052-curator-is-three-places-not-a-nine-state-queue.md)) called this out as a prototype
shortcut in the same breath as it shipped it, and left a standing request: **ask the user for a
mark-only asset, ideally SVG and transparent, and replace the crop.**

**The app icon** was an amber bulb drawn procedurally by `packages/desktop/scripts/make-icon.mjs` —
a rounded square, a radial glow, a highlight — standing in for a real icon
([ADR 0008](0008-desktop-app-supervises-services.md), update of 2026-07-17). It was drawn against
`--bg` and `--amber`, the tokens of the _backstage marquee_ theme that ADR 0052 replaced, so by the
time it shipped it matched nothing in the app.

The user has now supplied the mark as an SVG: the disc alone, vectorized, no wordmark, no paper, a
single `currentColor` fill.

## Decision

**One asset, `packages/curator/ui/src/assets/marquee-mark.svg`, feeds both.**

1. **The SVG is normalized on the way in.** Inkscape's editor transform (`matrix(0.1,0,0,-0.1,…)`)
   is baked into the coordinates and the `sodipodi`/`inkscape` namespaces are dropped, so the file is
   four `<path>` elements in a viewBox that is exactly their bounding box. It carries no width, no
   height and no colour of its own — it fills whatever box it is given, in `currentColor`.

2. **The masthead inlines it** rather than pointing an `<img>` at it. An SVG loaded through `<img>`
   is a separate document and cannot see the host page's `color`, so `currentColor` there resolves
   against the initial value — black in a light UA, _white_ in a dark one. Inlined, the mark is
   `--pp-ink` because the brand block is, and it would reverse to paper anywhere the brand block
   does. The crop box, the `130px` offsets and the `mix-blend-mode` all go.

3. **The app icon is the mark in `--pp-paper`, centred on a rounded `--pp-ink` tile**, spanning 80%
   of the tile on its longer axis. The tile is not decoration. The mark is thin line art; at the 24px
   and 16px sizes Windows uses in the taskbar and the title bar its strokes blur into each other, and
   the tile is what keeps the icon present against a dark _and_ a light taskbar. A bare transparent
   mark was rendered and rejected: it disappears on a dark taskbar.

4. **`make-icon.mjs` rasterizes the SVG itself**, in pure Node — it parses the path data, flattens
   the cubics, fills them by the nonzero rule and encodes the PNG through `zlib`. No image library
   is added.

5. **The generator reads the masthead's copy of the asset** by relative path, across the package
   boundary. A second copy under `packages/desktop/build/` would be a second thing to remember to
   update, and the two would drift.

6. **Curator gets a favicon of the same picture**, generated by
   `packages/curator/scripts/make-favicon.mjs` into `ui/public/favicon.svg`. It is SVG in, SVG out —
   the mark's path data is reused verbatim under a transform, never re-emitted — so it stays the mark
   by construction. It carries explicit `#17150f` / `#f2efe8` fills rather than `currentColor`,
   because a favicon is a standalone document with nothing to inherit from, and it keeps the tile for
   the same reason the app icon does: the surrounding chrome may be light or dark.

   **It is not the packaged app's icon, and does not reopen the "tab" question.**
   [curator-ui-ux.md](../specs/curator-ui-ux.md) §2 is right that Curator has no browser tab, and
   `curator-spec.md` corrected itself on 2026-07-25 for assuming otherwise. This is for the two ways
   Curator is opened in a real browser and always has been — the Vite dev server on `:4738`, which
   `packages/curator/README.md` tells you to open, and `:4739` hit directly. Both showed a default
   icon. Nothing about where a count belongs changes: the header is still its home.

7. **Both generated artifacts are pinned by a freshness test.** Change the mark and forget to
   regenerate, and `packages/desktop/test/icon.test.ts` and `packages/curator/test/favicon.test.ts`
   fail with the command to run. Neither generator runs in CI — a GitHub runner never invokes
   `pnpm run dist` — so a test is the only thing that can hold this.

## Consequences

- **The logo is the logo in both places.** The mark scales, takes the ink of whatever it sits in, and
  is sharp at any zoom or DPI. `marquee-disc.jpg` is deleted; `docs/design_handoff_curator_overhaul/marquee-logo.jpeg`
  stays as the supplied original.

- **This supersedes the app-icon bullet in [ADR 0008](0008-desktop-app-supervises-services.md)'s
  2026-07-17 update.** That ADR's decision — that the desktop app supervises the services — is
  untouched; only "a generated amber-bulb `build/icon.png`" is no longer true. It closes ADR 0052's
  outstanding request in the direction that ADR asked for.

- **We own a small rasterizer.** It handles `M`/`L`/`C`/`Z`, which is all a traced outline emits, and
  throws on anything else rather than silently dropping a shape. It was checked against Inkscape's
  rendering of the same file at 256×272: mean absolute alpha difference **0.78/255**, with 0.15% of
  pixels differing by more than 40 — all of them on stroke edges, where the two antialiasing schemes
  disagree by design. The alternative was a build-time dependency (`sharp`, `resvg`) to run a step
  that produces one committed 32KB PNG, or hand-generating that PNG outside the repo where nothing
  could reproduce it.

- **A hand-drawn mark has a floor.** Four concentric arcs and a grid cannot survive being drawn into
  a 16×16 box. At that size the icon reads as a tile with a disc-ish smudge, which is a limit of _this
  logo at that size_, not of the pipeline. If it ever matters, the fix is a simplified small-size
  variant of the mark, and the generator is where it would be selected.

- **`renderIconPng()` stays unit-tested**, and the test now pins the property that the fill rule
  actually protects: the mark's counters stay open. Filling each subpath independently and unioning
  them — the easy way to get a traced outline wrong — turns the disc into a solid paper blob, and the
  test was watched failing that way before it was kept.

- **Regenerating is two commands, and forgetting them is a test failure, not a shipped mistake.**
  `pnpm --filter @marquee/desktop icon` and `pnpm --filter @marquee/curator favicon`. The icon gate
  compares decoded pixels rather than PNG bytes, so a Node version whose zlib packs the same image
  differently does not fail it.

- **The rasterizer is strict about what it accepts, and that caught two of its own bugs.** Writing
  the direct tests for `flatten()` turned up (a) a tokenizer that matched only `/[MLCZ]/`, so an `A`
  was dropped and its arguments were read as coordinates for the previous command, and (b) a
  `.toUpperCase()` that silently drew a relative `c` as an absolute `C`. Both produced a wrong shape
  that still rendered — the failure mode the whole-icon pixel assertions cannot see, because they
  only know what the current mark looks like. Unsupported and relative commands now throw.
